# 조향 캘리브레이션 절차 — 한국어 정리

공식 원문은 [docs/design/calibration.md](design/calibration.md) 1절이며 그쪽이 기준이다.
이 문서는 팀 작업용 한국어 정리이고, 값이나 절차가 어긋나면 원문을 따른다.

목적은 절대 각도 센서의 raw counts를 **라디안**으로 바꾸고, `0`이 **직진**이 되게 만드는 것이다.
road wheel 기준 동작 범위는 **±22.5° (±0.3927 rad)**이다 (dbw.md 12절, 수치 인터페이스 계약).

센서는 load-side에 장착한 AS5600 계열 자기식 절대 각도 센서이며, 포텐셔미터가 대체 수단이다.

## 순서

0절 wrap 검사 → 1절 영점 `c0` → 2절 스케일 `k` → 3절 명령 정규화 확인 → 4절 스윕 검증.

**이 순서를 지켜야 한다.** 뒤에 오는 최소 회전 반경 측정(원문 1.5절)은
"full lock을 명령한다"로 시작하는데, 그 명령이 실제로 ±22.5°를 만드는지는 2·3절이 보장한다.
2절을 건너뛰고 반경을 재면 무엇을 측정했는지 알 수 없다.

## 0. wrap 검사 — 다른 무엇보다 먼저

> **주의**
> 센서가 감지하는 축을 **전체 기계적 가동 범위**로 돌리면서 raw 값이
> **불연속 없이 단조**인지 확인한다. 측정한 가동 범위를 기록한다.

AS5600은 single-turn absolute다. 한 바퀴를 넘어가면 값이 접히고(wrap),
그 쓰레기 각도가 모터를 구동하는 위치 루프로 들어간다. FMEA 2행, 심각도 5다.

wrap이 있으면 센서가 **잘못된 축에 달린 것**이다. 보정으로 해결하지 않는다.
load-side로 옮기거나 포텐셔미터 대체 수단으로 바꾼다.

## 1. 기계적 중심(영점) `c0` 찾기

1. 바퀴를 **땅에서 떼고** 벤치 스탠드에 올린다. 조향 모터는 **무전원**으로 두어 free-wheel 상태로 만든다.
2. 손으로 앞바퀴를 물리적으로 직진에 맞춘다. 앞 타이어 두 개에 직선자를 걸치거나,
   먼저 짧은 직선을 주행해서 중립을 표시한 뒤 맞춘다.
3. 바퀴가 직진인 상태에서 절대 센서의 raw counts를 읽는다. 이 값을 `c0`(영점 오프셋 counts)로 기록한다.
4. `c0`를 Teensy의 ROS 2 zeroing 서비스로 저장한다 (dbw.md 10.1절). Teensy가 EEPROM에 유지하므로
   재부팅 후에도 중심이 살아남는다.

4단계가 ADR B로 얻는 이점이고, B-MROVER의 부팅 시 중심이 임의로 잡히던 문제(finding F4)를 직접 고치는 지점이다.

## 2. counts→degrees 스케일 `k`

포텐셔미터는 ±22.5°의 좁은 구간에서 거의 선형이므로 2점 피팅으로 충분하다. 선형성 확인용으로 점을 더 딴다.

1. 바퀴를 **full left lock**까지 돌리고, 디지털 각도계(바퀴에 각도기나 경사계)로 **실제 road-wheel 각**을 측정해
   `(θ_L, c_L)`로 기록한다. 이상적으로 `θ_L ≈ +22.5°`다.
2. **full right lock**까지 돌려 `(θ_R, c_R)`을 기록한다. 이상적으로 `θ_R ≈ −22.5°`다.
3. 중간 3~5점을 더 기록해 선형성을 확인한다. 잔차는 약 0.5° 미만이어야 한다.
4. `θ(counts) = k · (counts − c0)`로 피팅한다. 여기서 `k = (θ_L − θ_R)/(c_L − c_R)`이며 counts당 degree다.
5. 비선형성이 문제가 되면 작은 lookup table이나 다항식을 대신 저장한다.
6. `c0`와 `k`(또는 LUT)를 `config/calibration/steering.yaml`에 저장한다.

Teensy가 `θ = k·(raw − c0)`를 적용한 뒤 `DbwStatus`의 `steering_angle`을 **라디안**으로 발행한다.

이상적인 값이 `±22.5°`라고 적혀 있지만, 측정값이 그와 다르면 측정값이 맞다.
22.5°는 설계 목표이고 이 섀시의 실제 lock이 아니다.

## 3. 명령 정규화 확인

명령 사슬 전체를 확인한다.

| `DbwCommand.steering_angle` | 기대 road-wheel 각 |
|---|---|
| `+0.3927` rad | `+22.5°` |
| `0` | `0°` |
| `−0.3927` rad | `−22.5°` |

명령값 대비 측정값 곡선을 기록한다. 원점을 지나는 직선이어야 한다.
오프셋이 보이면 `c0`를 다시 확인한다.

## 4. 검증

`0 → +22.5 → −22.5 → 0` 스윕을 명령하고, 측정한 road-wheel 각이 **±1°** 안에 들어오며
중심에서 `0°`로 돌아오는지 확인한다. 스윕 로그를 보관한다.

## 산출물과 기록

| 항목 | 저장 위치 |
|---|---|
| 영점 `c0`, 스케일 `k` 또는 LUT | `config/calibration/steering.yaml` |
| 측정한 기계적 가동 범위 (0절) | 같은 파일의 주석 또는 캘리브레이션 기록 |
| 스윕 로그 (4절) | 캘리브레이션 기록 |

각 산출물에는 날짜, 작업자, 차량 serial, 펌웨어·소프트웨어 git commit을 함께 남긴다.
하드웨어가 바뀌면 캘리브레이션을 재현하거나 무효화할 수 있어야 한다.
타이어 교체, 센서 재장착, 펌웨어 재기록 뒤에는 해당 절을 다시 수행한다.

`config/calibration/` 디렉터리는 현재 저장소에 없다. 원문 7절이 이 경로를 산출물 위치로 지정하지만
아직 만들어지지 않았으므로, 처음 저장할 때 디렉터리를 함께 만든다.

## 주의

- 이 절차는 `vehicle<n>.yaml` overlay에 들어가는 값이 아니다. overlay에 쓰는 것은
  `wheelbase`나 `min_turning_radius` 같은 **치수**이고, `c0`·`k`는 캘리브레이션 산출물이다.
- `steer_limit_deg`는 overlay 대상이다. 2절에서 측정한 실제 lock 각이 설계 목표 22.5°와 다르면
  그 측정값을 overlay에 기록한다.
- 2절 1·2단계는 바퀴를 들고도 수행할 수 있지만, 최소 회전 반경 측정(원문 1.5절)은
  바퀴를 바닥에 놓고 4 m × 4 m 이상의 빈 바닥에서 보행 속도로, 작업자가 옆에 따라붙은 상태로 한다.
- 캘리브레이션은 **scale 오차**의 범위를 정하는 작업이다. drift는 EKF가 담당한다.
  raw 조향·휠 오도메트리가 정확해지기를 기대하지 않는다.
